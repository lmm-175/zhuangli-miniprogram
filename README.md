# 妆历 ZHUANGLI · 项目可视化手册

化妆师的排班本 + 接单本。

一个妆娘一天要接十几单。她现在的工具是一张纸加满屏微信聊天记录。 妆历把「排班」和「接单」接过来：填六个数字，排出一整天的妆位表；顾客点开一条分享链接，自己挑还空着的那个。

## 项目概述：把「排班」和「接单」从聊天记录里接过来

妆历不是「找化妆师」的平台，而是一个 只服务已经发生的预约 的工具。 顾客从哪里来，交回给小红书、漫展群和微信；妆历只负责让「排一场、发出去、收一张单」这件事变顺。

产品定位

### 同城化妆师的排班本 + 接单本

一场漫展 = 一个档期；一个档期 = 若干个妆位。妆娘填六个数字，整天的时段表自动排出来；顾客在分享页上挑一个还空着的妆位，填表提交。

目标用户

### 接单的妆娘，以及她微信里的顾客

C 端顾客不需要注册、不需要登录、不需要授权头像昵称；B 端妆娘用它排版、发链接、管单、标记定金与完成状态。

核心价值

### 线上排档期 · 双向确认 · 线下自行结算

没有微信支付、没有平台抽成、没有资金流。定金只记录「有没有付」，不记录金额承诺。顾客与妆娘在微信里完成沟通和转账。

### 它替掉的，是一张纸和一屏聊天记录

| 妆娘现在怎么做 | 妆历让她怎么做 |
|---|---|
| 在备忘录里手写「5 月 2 日 10:00 / 10:30 / 11:00…」 | 填六个数字，自动排出整场妆位表 ，改一个数整表重算 |
| 顾客微信问「我约几点」，她翻聊天记录 | 顾客点开分享页，自己挑还空着的妆位 |
| 谁付了定金、谁做到哪一步，全靠脑子记 | 6 个订单状态 + 4 张 Tab + 批量推进 ，每一步都有落点 |
| 同一个漫展十几单，混成一团 | 按场次 筛、按顾客 CN 搜，两个条件相乘 |
| 同样的排班，下次再手写一遍 | 存为模板 ，下次选日期、确认名字，一键生成 |

### 技术选型：把「小」做到极致

### 微信小程序原生

WXML / WXSS / JS，不用框架、不用构建。项目里没有 package.json，没有 node_modules。

### 零第三方依赖

不引 UI 库、不用 TypeScript。自定义导航栏、自绘 tabBar、人像剪影头像全部手写。

### 本机 storage 为主

7 个 zhuangli_ 前缀的 key。唯一会写云端的通道是「问题反馈」，只写正文和时间。

### 纯 Node 自测

1,395 条断言，不用测试框架。改排班、预约单、填写页、导航、分享，必须重跑。

三条不可越的边界（红旗级）： ① 零金额—— 顾客可见页面不出现价格、金额、支付、收款； ② 零社交 / 零 UGC 公开展示—— 不评论、不关注、不私信、不展示任何人上传的图片； ③ 不做目录—— 任何「能被一页页翻完的妆娘列表」都不存在，每个列表的长度都必须由「你自己约过谁」决定。 这三条不是产品口味，是个人主体类目白名单决定的生死线，详见 §5.5。

## 用户角色：两种身份，两条底栏，同一份代码

进小程序的第一屏先问「你是谁」。选完就进各自那一端，两端从此互不打扰。 但「互不打扰」是界面上的事 —— 底层共用一份 storage、一条 tabBar 组件、一个设置页、一个填写页。

### 妆师（B 端 · 接单的人）

她的工具：排班、发链接、管单

- 新建档期：漫展名 / 日期 / 起始时间 / 妆位时长 / 休息间隔 / 妆位数
- 改某个妆位的时间，后续时段自动顺延，但停在已预订的「锚点」为止
- 把这一场分享给顾客，收结构化预约单
- 确认 / 拒绝 / 标记定金 / 标记完成，批量推进
- 替线下谈好的顾客「代填」一张单

底栏 3 格： 档期 · 预约单 · 我的
 第一屏： 档期（有档期看列表，没档期看新手引导）

### 约妆端（C 端 · 找她约妆的人）

她的入口：一条分享链接，不需要注册

- 点开妆容卡片 → 落在 C1 妆位页
- 按场次筛，挑一个还空着的妆位
- 填 CN（圈名）/ 角色名 / 微信号 / 妆感 / 眼型 / 备注
- 提交后妆娘主动联系；在「我的预约」看自己提交过的单
- 可申请取消，由妆娘同意或不同意

底栏 3 格： 我约过的妆娘 · 我的预约 · 我的
 第一屏： 我约过的妆娘（私人记录，不是平台目录）

### 权限与能力对照

| 能力 | 妆师 | 顾客 | 说明 |
|---|---|---|---|
| 浏览公开妆位页（C1） | ✓ | ✓ | 顾客从分享卡片进入；妆师从自己档期详情页的「分享」进入 |
| 新建 / 修改档期 | ✓ | — | 只有妆师端有「档期」tab |
| 提交预约单 | ✓（代填） | ✓ | 同一个 booking-form ，两种 mode |
| 推进订单状态 | ✓ | — | 顾客只能「申请取消」，不能直接改状态 |
| 查看顾客微信号 | ✓ | — | 妆师端预约单详情；顾客看不到其他顾客的信息 |
| 查看妆师微信号 | — | ✓（受开关控制） | 妆师可在设置里关闭「在分享页展示微信号」 |
| 查看 / 修改自己的资料 | ✓ | — | 昵称 / 城市 / 接妆风格 / 简介 / 头像颜色 |
| 切换身份 | ✓ | ✓ | 两个「我的」页各有一行 |
| 问题反馈 | ✓ | ✓ | 全项目唯一真的会写云端的通道 |

一键切换身份，但每次都先问一次。小程序全局只有一个 tabBar，而两个角色需要的格子不一样。项目走官方"custom": true 自绘 tabBar， 由 utils/tabbar.js 按角色给出 3 格清单，custom-tab-bar/ 负责画出来。 页面用 wx.switchTab 跳转 —— 在 tab 页上用 navigateTo / redirectTo 会静默失败，页面不动、控制台也不报错。

为什么不做「记住我，下次直接进」？ 2026-09-29 真机调试时定的：每进一次都想得起来「还有另一端」。自动跳过会把「切换身份」变成藏起来的暗门，而妆娘和顾客共用同一台手机的场景并不罕见。

## 业务流程图：一条主线，三个分支，六个状态

主线只有一件事：妆娘排一场 → 发出去 → 顾客挑一个妆位 → 提交 → 妆娘确认 → 线下结算 → 完成。 分支全部发生在「这张单还要不要占着那个妆位」上 —— 这是整个产品最需要说清楚的一件事。

## 页面原型：按顾客与妆娘的真实使用顺序

下面 8 屏覆盖了主路径。手机框是按小程序实际样式复刻的 HTML 原型，不是外部截图 —— 每个字段、每个状态、每个按钮的文案都与代码一致。

先说明一处与常见模板的差异： 常见模板里会写「首页推荐化妆师 / 作品集 / 上传支付凭证 / 核验收款」。这四个在本项目里 有明确的产品决定 ： 首页不做推荐（个人主体不能做公域目录）、C1 不做作品集（用户上传图片给顾客看＝UGC 公开内容）、 不做支付凭证上传（没有资金流承接方，且图片 UGC 会引入内容安全审核）。 取而代之的是「私人记录列表」「简介 + 妆位表」「线下自行结算 + 定金状态」。原因见 §5。

### 模板要求 → 本项目落点

| 常见模板里的页面 | 本项目的页面 | 差异 |
|---|---|---|
| 首页：推荐 / 搜索 / 分类 | 角色选择 → 我约过的妆娘 | 不做公域推荐；列表是私人记录，只按昵称 / 城市搜索 |
| 化妆师详情：作品集 / 日历 / 预约 | C1 妆位页 | 无作品集；由简介 + 场次切换 + 妆位表承担 |
| 预约提交：服务 / 时间 / 备注 | 填写预约单 | 时间在 C1 上选好；表单零金额 |
| 我的预约 / 订单列表 | 我的预约（顾客）· 预约单（妆师） | 顾客只读；妆师四 Tab × 场次 × 搜索 × 批量 |
| 订单详情：上传凭证 | 预约单详情 | 无凭证上传；改为顾客档案快照 + 定金状态 |
| 化妆师后台主页 | 档期 | 首屏就是档期，没有独立的「工作台」聚合页 |
| 订单核验：看凭证 / 确认收款 | 预约单详情 | 核验的是顾客填写的内容与定金状态，不是收款凭证 |

冷启动必然落到这一屏。没有底栏 —— 底栏是「两端各一条」的，而站在这一页时她还没选边。

1. 点「 我是妆师 」→ wx.switchTab 到档期页，记录 zhuangli_role = artist
2. 点「 我是约妆 」→ wx.switchTab 到我约过的妆娘页，记录 zhuangli_role = guest
3. 底部那行「上次以…进入」只是 提示 ，不是按钮；有过记录才出现

两个落点都是 tab 页，必须用 switchTab。用 navigateTo / redirectTo 会静默失败 —— 页面不动、控制台也不报错。

顾客端的第一屏。它不是「平台上有哪些妆娘」，而是一份 私人记录 ：列表从「我提交过的预约单」里聚合出来。

1. 点右上角「 搜索 」展开输入框，按昵称 / 城市 输入即筛
2. 点任意一行 → 进入她的 C1 妆位页（带 ?artist_id= ）
3. 没有搜索结果时，空态明写「搜人只按昵称和城市，不按风格」—— 不按风格筛人是刻意设计

这一页的长度 = 你自己约过几个人，不是平台上注册了几个人。一次都没约过的人永远不出现。 这不是功能取舍，是个人主体「不做目录」红线在界面上的唯一合规形态。

全项目 唯一会被陌生人打开 的页面。它承担了「化妆师详情 + 档期日历 + 预约入口」三件事，但刻意没有作品集。

1. 顶部是妆师的昵称 / 城市 / 接妆风格；微信号受妆师开关控制， 关掉时整行不出现 （不是变灰）
2. 点场次下拉，切换这一场； 可约的按时间在前，午休当分隔条，已占的沉底
3. 点「 选这个妆位 」→ 进入填写页，带上 (schedule_id, seq)
4. 「我约的」= 金色「已预约」；「别人约的」= 灰色「已被预订」；两者都不可点

从朋友圈点进来会先经过微信「单页模式」（scene 1154）。这一页要做三处降级：不画导航栏、不画复制微信号、不画「选这个妆位」—— 判据是同一个 sp，在 onLoad 里算。

顾客自填（从 C1 点进来）和妆师代填（从预约单页点「代填」）走同一页，靠 mode 分叉。

1. 顾客模式：顶上「你选的妆位」是只读的，位子已经在 C1 上选好
2. 代填模式：顶上换成两个原生 picker —— 先选场次、再选妆位 ，下拉里只有还空着的
3. CN（圈名） 第一位、必填、单独报错 ；微信号是妆娘加人的唯一凭据
4. 点「提交预约单」→ 并发重查 ：这一场还在吗？这个妆位还空着吗？ → 都过才建单
5. 提交成功 → 妆位当场从「可约」变金色「已预约」，档期卡片的「N 人已预约」+1

页面上没有任何价格、金额、支付承诺。另需服务只显示项目名和「用户自备」提示，价格是妆娘线下的事。

顾客自己提交过的单，只读。状态棋子与妆师端用的是同一套文案，顾客不会看到第二种说法。

1. 列表按提交时间倒序，显示漫展名、第几位、时段、当前状态
2. 空态给一个「 去找妆位 」按钮 —— 它跳 tab 页，所以必须是 switchTab
3. 顾客 不能在这一页改单、撤单 ；取消要走「申请取消 → 妆娘同意」两步

这一页曾经是「我的」的下一层，2026-10-01 升成 tab 2。升 tab 会连带四类不报错的错： 跳转 API 静默失败、tab 页不许有返回箭头、旧入口要删、空态兜底也要改 switchTab。

妆师端的第一屏，也是整个 M0 的起点：她建过的所有场次，一屏看完「哪几场、每场几个妆位、有几个人约了」。

1. 左上「 模板 / 新建 」：两个动作都放左边，避开右上角微信胶囊
2. 点卡片任意位置 → 档期详情（时段表，可改 / 删 / 插妆位）
3. 点「 取消场次 」→ 二次确认；这一场还有占着妆位的单就拦住她
4. 卡片上的「N 人已预约」和拦住她时的张数 走同一个函数 ，不许各算一遍
5. 取消完不退回， onShow() 就地重画列表

「取消场次」用 catchtap，因为整张卡片是 bindtap="goDetail" ； 用 bindtap 会冒泡成「又开详情、又弹取消框」。按钮外壳用 padding-left 把点击区扩到 88rpx 以上，不是 margin。

这一页的四件事是 相乘 的：四个状态 Tab × 场次下拉 × 关键词搜索 × 批量处理。

1. 左上「 全部场次 ▾ 」只管选场次；右边输入框只管搜人（CN / 漫展名），回车、放大镜、点历史三条路同一个 applySearch
2. 四个状态 Tab 切换列表；搜索范围跟着当前场次走，两个条件相乘
3. 点「 一键处理 」→ 进勾选态，进来就是全选； 未付定金的单直接勾不上
4. 处理完如实播报「10 单里处理了 8 单，跳过 2 单」，不许只报「处理完成」
5. 右上「 代填 」→ 打开填写页的妆师模式

搜索拆成两级状态： kwInput 打字只重算面板清单，kw 提交才真搜。 合成一个会每敲一个字符重建一次主列表。

顾客填的东西在这里一字不差地给她看 —— 提交时快照，顾客后来改了资料，这张单也不变。

1. 顶部是场次 / 时段 / 当前状态；下面依次是顾客档案、联系方式、定金
2. 点「 复制去加 」→ 微信号进剪贴板，妆娘去微信加人
3. 点定金开关 → 切换「已付 / 未付」； 未付定金时，「标记已完成」是灰的 ，代码路径也再挡一道
4. 待处理状态显示「拒绝并释放」+「标记已确认」；点确认 立刻退回列表 防手抖
5. 顾客申请取消时显示「不同意，继续保留」+「同意取消」

取消走 cancelled 软删除，不删记录。妆娘经常遇到跑单，删记录等于把唯一的凭据也删了。

## 核心功能与规则：把「没有支付」做成一套可用的流程

这个项目最特别的地方，是产品形态被审核规则倒推着长出来。支付、公域发现、作品集三块被拿掉之后， 留下来的每一个功能都必须回答同一个问题： 在没有交易、没有社交、没有目录的前提下，怎么让一张预约单走完？

### 5.1 支付模型：从「上传凭证」改成「线下结算 + 定金状态」

### 常见模板里的写法

1. 顾客选服务、下单
2. 顾客上传支付凭证
3. 妆师核验收款
4. 订单生效

### 妆历的实际做法

1. 顾客选妆位、提交预约申请
2. 妆师确认接单（双向确认）
3. 双方在微信里沟通、线下转账
4. 妆师只标记「定金已付 / 未付」
5. 到店完成后标记「已完成」

| 问题 | 回答 |
|---|---|
| 为什么不做微信支付？ | 个人主体没有「电商平台」类目，一有交易就落进去；且平台一旦涉及资金流，退款、纠纷、结算都是不能承受的复杂度。 |
| 为什么不做支付凭证上传？ | 凭证是用户上传的图片，会引入内容安全审核（mediaCheckAsync /imgSecCheck ）；而线下微信转账本身有记录，再传一张图没有承接方，收益抵不过成本。 |
| 那怎么防止跑单？ | 靠「确认接单 + 定金状态 + 完成状态」三步留痕。妆娘能看到谁付了定金、谁还没付；订单记录不删除，跑单时是唯一凭据。 |
| 顾客页面上会有金额吗？ | 没有。顾客可见页面零金额、零价格、零支付承诺。妆师端自己记账（定金有没有付）不构成对顾客的服务要约。 |

### 5.2 订单状态流转规则

| 状态 | 谁来推进 | 妆位 | 说明 |
|---|---|---|---|
| 待处理 pending | 顾客提交 | 占用 | 妆师可「标记已确认」或「拒绝并释放」 |
| 已确认 confirmed | 妆师 | 占用 | 等线下收定金、到店；未付定金不能标完成 |
| 已完成 done | 妆师 | 占用 | 终态；ALLOW 表挡住「已完成被拉回已确认」 |
| 已拒绝 rejected | 妆师 | 释放 | 终态；妆位立刻可以再被约 |
| 申请取消 cancel_requested | 顾客 | 仍占用 | 留在「已确认」Tab，等妆师同意 / 不同意 |
| 已取消 cancelled | 妆师同意 | 释放 | 软删除，记录保留；妆位空出来 |

只有 rejected / cancelled 才真的把妆位放出来。这个判据只有一处实现（ utils/bookingStore.js 的 BOOKED_STATUS ）， 同时服务三件事：档期详情页画「已预订」、C1 画可约标记、提交时的并发校验。 ⛔ 不许任何页面自己再写一遍。

### 5.3 排班规则：已预订的妆位是「锚点」

### 改时长 → 顺延，但停在锚点

改某个妆位的时间，后面所有妆位自动顺延；顺延到第一个「已预订」的妆位为止。已预订的妆位自己、以及它后面所有妆位的时间都不许动。

跟客人已经约好的时间，不能被一次排班调整悄悄改掉。

### 删 / 插妆位 → 后面时间不动

删掉一个妆位会留出一段空档；「＋」只能把新妆位塞进空档里，不能把后面的妆位整体往前拉。

已经排好的时间是一种承诺，增删不能改变别人的时段。

### 午休是独立一行

浅蓝色独立行，可改起点和时长、可取消，不占一个妆位序号。午休能落在任意妆位之后，包括最后一个。

「在第几个妆位后」的选项跟着妆位数算，不是写死 1..8。

### 5.4 分享与转发

FORWARD

### 18 个页面都能转发，落点统一到 C1

「能不能分享」不是一个全局开关，而是每一页各自定义 onShareAppMessage。 全项目 18 个页面都接上了 utils/share.js，转发卡片统一落到 C1 妆位页。

TIMELINE

### 朋友圈只给 C1 开

朋友圈分享 不能自定义落点。如果妆师从管理页发到朋友圈，别人点开看到的是她的管理界面、按钮全是死的。 所以 onShareTimeline 只在 C1 定义，其余 17 页不定义。

朋友圈点开不是直接进小程序。会先进微信「单页模式」（scene 1154），要点那条「前往小程序」。C1 在这个模式下做三处降级（导航栏 / 复制微信号 / 选这个妆位）， 判据是同一个 sp，在 onLoad 里算。
 ⚠️ 小程序也 不能自己弹出分享面板 ：妆师点「分享」后，另一半必须她自己点右上角「···」。

### 5.5 个人主体的限制，如何变成产品边界

| 红线 | 在界面上体现为 | 被砍掉的东西 |
|---|---|---|
| B1 零金额 | 顾客页不出现价格 / 金额 / 支付 / 收款 | 支付、收费、平台抽成 |
| B2 零社交 / 零 UGC 公开 | 不评论、不关注、不私信、不展示任何人上传的图片 | 作品集、妆面样片、头像上传、评价体系 |
| B3 不做目录 | 「我约过的妆娘」长度 = 你自己约过几个人；不按风格筛人 | 妆娘目录、推荐、附近的人、按风格找人 |

第一次提审驳回的原话： 「涉及用户自行生成内容（图片）的记录、分享，属 社交-笔记 范畴，为 个人主体小程序未开放类目。」 于是整条产品线掉头，砍掉了三块本来做好的东西；每砍一块都写清了为什么，避免以后重新捡回来。

## 项目难点与优化：每一个坑都沉淀成了一条规矩

这个项目最值钱的部分不是页面数量，而是「同一个问题不再犯第二次」。 下面 7 个难点，每一个都写清了现象、定位、改法，以及最后沉淀成的那条可复用规矩。

### 类目限制倒推产品形态：先决定「不做什么」

#### 问题

最初做的是「同城化妆师平台」：公域发现、作品集、在线支付。第一次提审被驳回，理由是用户上传图片的展示与分享属于「社交-笔记」，个人主体未开放；平台形态则根本没有对应类目。

#### 改法

把产品重定义为 纯工具 ：砍掉公域发现、作品集、支付；把「我约过的妆娘」做成私人记录，把作品集换成简介 + 妆位表，把支付换成线下结算 + 定金状态。三条红线写进 PRD，任何新需求先对照。

沉淀： 产品形态不是先想出来的，是被审核规则倒推出来的。先确定不可越的边界，再在边界内把剩下的东西做锋利。

### 双角色导航：小程序全局只有一个 tabBar

#### 问题

妆师端要「档期 / 预约单 / 我的」三格，顾客端要「我约过的妆娘 / 我的预约 / 我的」三格。原生 tabBar 只能配一份清单，无法按角色切换。

#### 改法

走官方"custom": true + 根目录 custom-tab-bar/，由 utils/tabbar.js 按角色给出清单，页面用路由认当前格。代价是自定义 tabBar 不替页面扣底部高度，所以每个 tab 页根容器都要带.tabbed。

沉淀： 「升成 tab 页」会连带四类不报错的错：跳 tab 页用 navigateTo / redirectTo 静默失败、tab 页不许有返回箭头、旧入口要删、空态兜底也要改 switchTab。全项目扫描必须同时扫这两种 API。

### 排班算法：已预订妆位是锚点

#### 问题

妆娘改一个妆位的时长，后面所有时段都要顺延；但有些妆位已经被顾客约走了，跟客人约好的时间不能被悄悄改掉。删 / 插妆位时也不能把后面整体拉来拉去。

#### 改法

把「已预订」的妆位定义为 锚点 ：改时长只顺延到第一个锚点为止；删 / 插妆位后面时间一律不动，新妆位只能塞进空档。纯函数落在 utils/schedule.js，自测第一段钉着。

沉淀： 业务规则要先变成可测的纯函数，再谈界面。界面上「确认看得见、点不到」的问题，往往是布局把按钮挤出了可视区，不是事件没绑。

### 「点了没反应」四连：每一次病都不一样

#### 现象

同一个说法在项目里出现过四次：① wx.hideKeyboard() 打断触摸序列，紧跟的 showModal 被整个吃掉；② 名字 flex:1 把按钮顶到卡片最右边，中间全是「看着像按钮、点下去是卡片」的空白；③ 按钮总高只有 45rpx，远低于微信 88rpx 点击区建议；④ 卡片过期时静默兜底，把「卡片过期」和「按钮坏了」压成同一种表现。

#### 改法

删掉没有必要的 hideKeyboard；名字改 flex:0 1 auto + min-width:0，按钮紧贴名字；按钮外套点击壳，用 padding 扩到 88rpx 以上；每个分支都必须出声，不许静默 return。排查时先把探针写在屏幕上，而不是让用户去 Console 找日志。

沉淀： 听到「点了没反应」，先追问「结果变成了什么 / 别的键也点得动吗」。用户往往在同一条消息里已经把答案说了 —— 「容易误触进入此场次」就是那句答案。

### 软删除记录被写回 storage：唯一凭据差点被真删

#### 问题

档期取消用的是软删除（ status:'cancelled' ）。但 addSchedule / updateSchedule 拿 过滤掉 cancelled 的 列表当底稿写回 storage，等于把软删除的记录真删了。触发路径隔着一整页：取消 A → 点开 B 的详情页（onLoad 里就有一次 updateSchedule）。

#### 改法

拆出 rawList() ：展示用过滤后的列表，写回用原始列表。自测里用「探针场次」在中间插一次别的写操作才抓得到 —— 只在取消完那一瞬间查，是抓不到的。

沉淀： 「读写用同一份数据」是最容易埋雷的地方。展示层的过滤不能顺手带进写回路径。测试用例要覆盖「中间插一次别的写操作」的真实时序。

### 分享体系：能不能分享是 18 页各自的一件事

#### 问题

用户反馈「不能转发」。排查发现：微信只有定义了 onShareAppMessage，右上角菜单才显示「转发」。项目里原先只有 1 页定义了，所以点「···」根本没有转发项，也不报错。

#### 改法

抽出 utils/share.js，18 页全接上，落点统一到 C1；朋友圈只给 C1 开 onShareTimeline，因为朋友圈不能自定义落点。另加一条自测扫描：所有页面必须有 onShareAppMessage，且除 C1 外不许有 onShareTimeline。

沉淀： 「能不能分享」不是开关，是每一页各自的一件事。死代码会连带别人的文档一起说谎 —— 清理时要把入口、样式、文档、隐私声明一起清掉。

### 质量保障：1,395 条断言 + 突变测试 + 远程 clone 验证

#### 做法

纯 Node 运行 妆历 自测.js，不用测试框架。覆盖排班纯函数、预约单状态机、填写页、导航栏、tabBar、分享、源码结构扫描。每条修复都配一条会「咬人」的断言；关键守卫做突变测试：故意改坏源码，确认断言会红。

#### 流程

改代码 → 跑自测 → 本地 commit → 推送私有仓库 → 验远程文件数与 blob 哈希 → clone 到临时目录再跑一遍同样条数。文档同步更新 README 的「第 N 处沿革」与 PRD 状态。

沉淀： 靠人眼发现的检查项不算检查项。能写成断言的，就不要留给记忆；能扫源码钉结构的，就不要只靠界面走查。

### 6.1 开发流程与版本管理

### 个人主体审核驳回，平台版转向纯工具版

砍掉公域发现、作品集、支付；把审核约束从「定性判断」下沉为「类目白名单」，写成 B1 / B2 / B3 三条红线。

### M0 范围确定，界面稿与 PRD 成型

M0 试提审定为 2 天 2 屏（工作台空态 + 分享落地页），交付标准是「点哪里都不白屏」；随后扩展为 18 页的完整走查稿。

### 小程序落地，真机调试，连续修真实渲染与交互 bug

自定义导航栏、双角色 tabBar、排班锚点、预约单状态机、批量处理、搜索历史、分享落地页逐步成型。

### 分享体系、隐私合规、文档一致性整轮

18 页转发统一落点；朋友圈只开 C1；隐私指引删掉不成立的收集声明；界面稿 v2.0、PRD 重写为「需求 + 现状对照」。

### M0 审核通过，小程序正式上线

个人主体、类目「工具 - 预约/报名」，首版 18 页全部可用：妆娘排班 → 分享妆位 → 顾客选位 → 预约单处理，主流程闭环跑通。数据仍在本机 storage，只有「问题反馈」写云开发。

### 上线后维护：小步改动，每次都给一个可回滚的版本

1,395 条断言保持全绿；下一步是订阅消息、云同步、顾客端独立详情页，仍然守 B1 / B2 / B3 三条红线。

### 版本管理

本地 Git 仓库 + 私有远程仓库。每改完一处就 git add . + git commit，提交信息写「改了什么」，留一个可回滚的版本。
 推送后核对远程文件数与关键文件哈希，再 clone 到临时目录跑一遍自测 —— 「push 成功」不等于「备份上了」。

### 文档与代码同步

每个修复都同时落三处：自测里一条会「咬人」的断言、README 的「第 N 处沿革」、本手册里对应的流程或规则。
 文档不单独维护「理想状态」，只记录代码此刻真实的样子 —— 否则下一个人会照着一段过期的说明改代码。

关于订阅消息：M0 刻意不做，上线版本里也没有。订阅消息模板库按类目发放，换成「工具 - 预约/报名」后「预约提醒」还能不能申请到，要重新查； 而且一次性订阅每次都要用户点击，在提审阶段引入会多一项审核内容，也容易做出「点了没反应」。 代码里只在 onSubmit 留了位置注释，M1 再做。

## 复盘：数字、取舍与下一步

### 做对了什么

① 先把合规边界写死，再做功能，避免反复推翻；
 ② 把业务规则做成纯函数，界面只是它的投影；
 ③ 每一个 bug 都沉淀成一条规矩和一条断言，而不是「这次改好了」；
 ④ 数据最小化：本机 storage 优先，微信号单出口，云端只收反馈正文。

### 还可以更好

① M0 无后端，多设备 / 多人协作要等 M1；
 ② 顾客取消入口目前依赖妆师端两步流程，顾客端还没有独立详情页；
 ③ 订阅消息、真实头像上传、云同步都在 M1 的清单里，但必须继续守 B1 / B2 / B3。

「把能做的做到锋利，比把不能做的硬做出来更重要。」

妆历的形态不是先想出来的，是被个人主体的类目规则倒推出来的。 砍掉支付、公域发现、作品集之后，它反而更像一个真正的工具： 妆娘填六个数字排一天，顾客点一条链接挑一个妆位，一张单从提交到完成，每一步都有落点。
