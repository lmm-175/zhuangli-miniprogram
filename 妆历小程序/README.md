### 入口
| 界面 | 路径 | 说明 |
|---|---|---|
| **角色选择** | `pages/role-select/` | **一进小程序第一屏**：选 约妆 / 妆师。妆师 → **档期**；约妆 → **我约过的妆娘**。⚠️ 两条都走 `wx.switchTab`（两边第 1 格都是 tab 页）。上次身份有提示，可一键续用。 |

> 🔴 **底部导航条全项目只有一条**（`custom-tab-bar/`，2026-10-01 第二十一处）：
> 小程序**全局只有一个 tabBar**，而两个角色要的格子不一样 ⇒ 只能 `"custom": true` 自己画，

> 和 `app.json` 的 `tabBar.list` 是**同一件事的两半**（自测逐项比序）。
> ⚠️ 自定义 tabBar 微信**不会**替页面扣底部高度 ⇒ 每个 tab 页根容器必须带 `class="app tabbed"`，
> 高度只有一处（`app.wxss` 的 `--tabh:50px`）。**新加 tab 页 = 注册 + 加 `tabbed`，两件事一起做。**
> ⚠️ 跳 tab 页只能 `wx.switchTab`。用 `redirectTo` 是**静默失败** ——
> 🔴 **`navigateTo` 一样**（第二十一处第二轮：「我的预约」升成 tab 页时，C1 上那个按钮
> 就是 `navigateTo`，点下去不报错、不跳转、屏幕上一个字都没有）。
> 自测**把三个 API 全项目扫一遍**钉着，⛔ 不是只扫 `redirectTo`。

## 3. ⚠️ 跟界面稿的偏差

| # | 界面稿画的 | 代码里做的 | 为什么 |
|---|---|---|---|
| 1 | 系统导航栏 | **自定义导航栏** `navigationStyle:custom` | 界面稿的「设置 / 新建 / 保存 / 我的预约」都在**导航栏右侧**，微信系统导航栏放不下右侧文字。代价：自己算状态栏高度 + 避开右上角胶囊按钮（`components/nav/nav.js`）。**右侧动作会贴在胶囊左边，比稿子里靠内一点。** |
| 2 | Tabbar 有 🏠📅📋👤 图标，**4 个 tab** | **纯文字无图标**；妆师端 3 个 tab（约妆端另 **3** 个，见第 10 / 10b 行）。**第二十一处起是自绘的**（`custom-tab-bar/`），外观照原生长相画 | ① `iconPath` 只认 PNG 图片文件，不认 emoji，为 4 个 emoji 自绘一套 tabBar 不划算。② 第 4 个 tab「工作台」已取消（见顶部说明）。③ 自绘是为了**两个角色各一条**（微信全局只有一个 tabBar）—— 但**没有丢掉 `wx.switchTab` 的语义**（硬约束 #15）：走的是官方 `"custom": true`，不是页面里画的假底栏 |
| 3 | **有 A1 工作台屏** | **没有这一页** | 真机调试后判定它是纯聚合页，无独有内容（详见顶部）。**界面稿那份 HTML 不许覆盖，所以它至今还画着 A1 —— 这是已知且有意保留的差异。** |
| 4 | — | **JS 不用 TS** | PRD §10.1 定的 TS 是给正式产品的。M0 是一次性验证包，TS 要加 tsconfig + 编译插件 + 类型声明，纯开销。**跟「不引 TDesign」是同一个取舍。** |
| 5 | 「我的」页有 **「我的作品 0 张 ›」** 一行（对应 `pages/my-works/` 空态页） | **这一行和那一页都删了**（`app.json` pages **15 → 14**） | 妆娘上传的图片一旦给顾客看，就是个人主体未开放的「社交-笔记」类目（UGC）；不给顾客看，作品集对她本人又零价值 —— 整块取消。见 §4 第十五处。**那份 HTML 不回去改** |

**沉淀成四十二条规矩**（下次写别的页面照办）：

1. **`.slot-row` / `.cell` 这类不换行的 flex 行里，⛔ 不要往里塞 `flex-basis:100%` 的新增块。**
   它不会换行，只会挤爆，然后被 `.grp{overflow:hidden}` 裁掉 —— 而且**裁掉的是按钮，你只会看到「点不动」**。
2. **挤压会让 `.btn.xs` 里的「确认」折行 → 行高变化。**
   本轮只在 `schedule-detail` 局部加了 `white-space:nowrap`。
   **是否提到 `app.wxss` 的 `.btn.xs` 上（一处改、全站受益）还没定** —— 全局改要重新走查所有用了 `.btn.xs` 的页面。
3. **「右侧要留出多少」这类固定占位（胶囊避让、状态栏、安全区），padding 挂到「整条容器」上，⛔ 不要挂进那一段里。**
   挂进 `flex:1 1 0` 的那一段，等于把占位算进了它的**最小宽度**；一旦最小宽度超过它的等分宽度，整条就往一边溢出（`min-width:auto` 不让它缩），**看起来就是「标题压按钮」或「按钮压胶囊」**。
4. **导航栏动作放哪边，决定标题该怎么摆 —— 两种排法，别混用。**
   - **动作放右边**（默认，`slot="right"`）：两段 `flex:1 1 0` 等分 + 标题**在正常流里**。
     `space-between`（空间为负时退化成起点排）和「绝对定位居中标题」这一对组合，在**窄屏 + 右侧两个动作**的前提下**数学上不可能不重叠**，别再回头试。
   - **动作放左上角**（`slot="left"` + `center="screen"`，档期 / 预约单用）：标题必须**脱流**绝对居中于整屏。
     ⛔ 别指望「左右各留一样宽的空白」把标题憋到中间 —— flex 是拿**内容最小宽度**当起点再加等份的，
     左边有 73px 动作、右边空着 → 标题恒偏 **动作宽 ÷ 2**（375px 屏上 36.5px），**跟屏宽、跟留白多少都无关**。
     这个数写成了自测第③段的断言，别再试第二遍。
     ⚠️ 这里的绝对定位和上面那个「别再试」的绝对定位**不是一回事**：当初坏的是**右段**（最小宽度 = 动作 73 + 避让 102 = 175px 撑爆整条）。动作在左边时它推不动标题，长标题由 `titleMax`（屏宽 − 两侧各一份避让宽）兜住。
5. **picker 的选项列表 ⛔ 不许写死，必须从当前数据算出来。**
   写死的 `[1..8]` 和「妆位数 3」并存，就制造了**一整个区间的选项是哑弹**：选了没反应、还存下脏数据。
   规矩是两条 —— 选项**按真实数据生成**，且每项要**写出用户看得懂的值**（「第 3 个之后」不如「第 3 个妆位之后 · 13:30 起」）；
   以及**凡是「第 N 项」这类序号，进纯函数前一律夹进合法区间**，让「越界」在页面这层就不存在。
6. **「点」和「拖」长在同一个元素上时，⛔ 不要挂 `bindtap`。**
   挂上的话，**拖完松手会顺手把页面也带进去** —— 那是最烦人的一种误触。全在 `touchend` 里判：位移过阈值算拖，没过算点。
   配套两条：① 拖动那一帧要用 **`catchtouchmove`**，`bindtouchmove` 只是"听一下"，页面照样跟着滚；
   ② 判成「点」的时候要**把抖动带出来的位移推回去** —— 拖动是每帧跟手的（起手才没有死区），可「点」不该把东西蹭歪一点点。
7. **固定几何（导航栏高度 / 胶囊避让 / 状态栏）⛔ 不要两边各算一遍。**
   `utils/navbar.js` 就是为这个抽的：可拖动的浮层要避开导航栏，它和导航栏组件必须拿到**同一个**数。
   抽的时候照旧拆成「纯函数 + 一层薄 `wx` 包装」—— 纯的那半进得了自测，不用打桩。
8. **绝对定位的子元素在 flex 容器里 ⛔ 不会自动居中。**
   它不参与 flex 排布，static position 落在内容盒的**左上角**。画那个「＋」的两根小条时就踩了：
   写 `position:absolute` + 百分比尺寸，位置得自己 `left:50%;top:50%;transform:translate(-50%,-50%)` 补上。
   另外 ⚠️ 加号**用两根小条画、别用文字「＋」** —— 各平台字体里那个字符的字重和基线都不一样，画出来两根粗细对不齐。
9. **「存一份以后要拿来重建东西」的数据时，凡是重建要用的字段，⛔ 一个都不能省。**
   模板就是个例子：只存了名称和妆位，可「应用」要重建的是**一整条档期** —— 起始时间、妆位时长、间隔、午休。
   少存一样，重建那一步就会**沉默地**缺一块（午休没了、时长靠猜），而且**看起来是能用的**，所以没人会发现。
   配套两条：① 存的时候就照「以后怎么用它」写全（`buildTemplateRecord()` 存在的理由）；
   ② 反推要有，但**只用来兜底不完整的旧数据**，模板自己记了值就一律用模板的
   —— 带午休的模板里 `seq2→seq3` 隔着午休，拿妆位间隔硬推会算出 70 分钟的「间隔」来。
   反面同样要守住：**反推不出来就不要编**（老模板没有午休 = 不生成午休行），编出来的假数据比缺数据更难发现。
10. **点完一个键会「原地换出另一个键」的时候，⛔ 别让用户留在原地。**
    「标记已确认」点完，同一个位置上就是「标记已完成」—— 手抖一下就把客人的单标成已完成了。
    做法是**退出去**（退回列表，想再动它得重新点进来，中间隔了一次「选择」），而不是原地重绘。
    配套两条：① 退回那半拍要有个状态标志（`leaving`）**先把危险的那个键换成灰字**，⛔ 不许出现「慢半拍就渲染出危险键」的窗口；
    ② 每个状态动作都写一张 `ALLOW` 表，**动作只允许从指定状态出发** —— 按钮是给用户画的，拦不住代码路径，
       而没出口的状态会**来回跳**（已完成 → 已确认 → 已完成），这种脏状态没人会发现。
11. **同一件事的判定，全项目 ⛔ 只许有一处实现。**
    「这个妆位是不是已经有人了」（`BOOKED_STATUS`）先前写在档期详情页里当本地常量，后来「已完成」那天忘了同步它，
    结果**做完的妆位被当空位放了出来** —— 而这一处判定同时被**档期详情页的画标记**、**落地页的可约标记**、
    **提交预约单时的并发校验**三处读着（M1）。三份实现不会同时错，所以错了也永远对不上号。
    做法：判定收进 `utils/bookingStore.js` 的 `bookedSeqsOfSchedule()`，页面只调它；
    ⛔ 页面里不许再出现 `status === 'pending' || status === 'confirmed'` 这种手写枚举。
    同理，**筛选条件要滤在「唯一的那份数据源」上**（`_groups`），⛔ 不要滤在渲染层 —— 渲染层只画一次，读取层有很多次。
12. **「替对方做决定」的动作，⛔ 必须二次确认，而且要把后果写在框里。**
    `wx.showModal` 的 `content` 要写清楚会发生什么（「这一单移入『已取消』，妆位空出来可以约给别人」），
    按钮文案也要是**动作本身**（「同意取消 / 再想想」），⛔ 不用「确定 / 取消」—— 后者在这是个问句的框里读不出选了哪个。
    反面同样要守住：**该留的凭据不许删**。妆位要放回去，但记录得留着（顾客跑单是常态，删掉记录妆娘手里就什么都没有了）。
    ⚠️ **但二次确认不是终点：决定不是她的，就不该由她来点那一下。**
    「顾客取消预约」原先长成妆娘替顾客撤单 —— 二次确认框只解决了**误触**，没解决**越权**（客人可能根本不知道自己的位置没了）。
    改法是把动作**拆成两步**：**本人先去点第一步**（顾客端「申请取消」），妆娘这边只剩「同意 / 不同意」。
    妆娘手上那两个键因此都**不是「替她决定」，而是「对她的申请表态」**，`content` 也跟着改成陈述后果。
    推论：**两步一旦落地，中间态就是一个正经状态**（`cancel_requested`）—— 它得有 Tab 归属（留在「已确认」）、
    得有「算不算有人」的答案（算，妆位还占着）、得有一行字明说「在她点头之前这个位置还占着」，
    ⛔ 不能只当个临时标志位飘着。
13. **绝对定位的子元素在 flex 容器里的 static position ＝「把它当成唯一的那个 flex item」。**
    ⛔ 想「挂在某一条下面浮出来」的浮层（下拉面板、气泡、菜单），必须跟那一条一起包进一个 `position:relative` 的容器里，
    面板用 `top:100%` 挂在**那个容器**上。直接把面板挂到页根 `.app`（`display:flex`）下面，
    它会从**整页最顶上**（导航栏那里）展开 —— 而且**不报错**，就是位置莫名其妙。
    ⚠️ 和第 8 条不是一回事：第 8 条是「它不会居中，位置得自己补」，这条是「它的静态位置**根本不是你想的那个**」。
14. **「能不能勾 / 能不能点」这类判定，画控件的那条路和真正执行的那条路 ⛔ 必须问同一个函数。**
    `pickableIds()` 图省事直接调 `cfg.canPick(b)`，**绕开了** `canPick(mode, b)` 里那道状态守卫 →
    「顾客申请取消」的那张单在「一键确认」里被**预先勾上**，点执行时 `applyBatch` 又按状态把它跳过 →
    弹出「已确认 1 单（1 单状态已变，跳过）」。这正是用户明确否掉的**静默少处理**。
    做法：判定只写一处，**两条路径都调它**。执行前**再查一遍**是对的（勾选态是页面状态，可能已经过期），
    但两次查的必须**是同一个函数** —— 一旦是两份，「预先勾上」和「执行跳过」就是两个互相打架的答案，而用户看见的是**结果少了一个**。
    ⚠️ 和第 11 条的区别：第 11 条说「同一件事别写两份实现」，这条说「**只有一份实现，它照样能被某条路径绕过去**」。
15. **沉底 / 排序的判据按「人还要不要动手」画，⛔ 不是按「是不是终态」。**
    「这一场处理完了吗」＝「**没有一张单还需要她动手**」（`OPEN_STATUS = pending / confirmed / cancel_requested`），
    ⛔ 不是「全部都是 done」—— 那样一个「3 单做完 + 1 单被拒」的场次会被当成还有事，**永远挂在最上面**。
    空集也算「没人要动手」，本来就该沉底；沉底的那几项要**带一句小字说明原因**，⛔ 不然「它为什么在最后」看着像 bug。
    ⚠️ 配套：**比「哪一场更新」⛔ 别比 id 字符串** —— `'sched-demo-0502' > 'sched-1780…'`，因为 `'d' > '1'`。
    要取 id 末尾的连续数字比（`idRank()`），或者干脆存个 `created_at`。
16. **手写的数据（mock / 预置 seed），字段形状必须跟「产生它的那个纯函数」一模一样。**
    预置示例档期里手写的 `lunch` 漏了 `min` → 档期详情页那一行午休显示成「12:00 – 13:00 · **undefined 分钟**」。
    纯函数 `generateSlots()` 造的是 `{enabled, afterSeq, min, start, end}`，手抄一份就少写一个 ——
    而**页面上照样能显示**，只是缺一块，这是最不容易发现的一类错。
    做法：抄的时候**对着那个纯函数的 `return` 抄**，⛔ 别凭记忆；能的话干脆**让预置数据走一遍那个纯函数**，别手写第二份形状。
    ⚠️ 同一类错上一轮也犯过（手写模板丢了 `slotMin` / `gapMin` / `lunch`，见第 9 条）—— 这两条是一件事的两头：
    **第 9 条管「存」，这条管「写」**，判据都是「将来重建它的人需要什么」。
    ✅ **这条规矩真的响过一次**（2026-09-30 第十七处）：`ARTIST_PUBLIC.style_text` 手写的是
    「建模感 / 浓系 / 展妆」（**点选顺序**），而 `buildStyleText()` 按词表顺序排 ⇒ 该是「建模感 / **展妆** / 浓系」。
    修的是**手写的那份 seed**，⛔ 不是纯函数（理由是第 16 条自己要保的东西：同一组标签换个点选次序
    就换一段文案的话，她在分享页上会看到自己什么都没改、字却变了）。
    📌 所以这条断言的价值不在「抓到了」，在**它是在造数据的那一轮就红给你看的** —— 否则这个不一致
    会一直躺到某天有人重装一次小程序、发现「风格那几个字怎么换位置了」。
17. **「取消它」和「删掉它」是两件事 —— 记录留着，靠唯一的那个读函数把它滤掉。**
    用户要的是「取消后**直接从列表消失**」，实现成 `status = 'cancelled'`（**软删除**），
    `getSchedules()` 那一层把它滤掉，⛔ 不是 `splice` 掉那条记录。
    理由不是洁癖：取消只是「这一场不办了」，**单子可能还挂着记录**，妆娘回头问「那天那场呢」总得有东西可查；真删了就什么都没了。
    回报是顺带的 —— 「档期列表看不见它」和「预约单的场次下拉里没有它」**一次成立**，
    因为两边读的是同一个 `getSchedules()`（这就是第 11 条要的「唯一数据源」）。
    ⚠️ 反过来也要接住：滤掉之后 `getSchedule(id)` 取不到它，详情页会走「档期不存在」那条路 —— **这是想要的**（取消完就退回了，不该再点得进来），
    但它是**副作用**不是设计，所以写进了自测（⑧-C），别哪天被人当成 bug「修」掉。
18. **「正在打的字」和「已提交的值」分成两级状态 —— 打字不搜，提交才搜。**
    用一个 `kw` 走天下的话：打到「千」主列表就已经翻过一遍了（她还没输完），
    而且**每敲一个字符重建一次列表**。做法：`kwInput`（正在打）+ `kw`（回车 / 点放大镜才写，驱动列表）。
    ⚠️ 三个配套，少一个就露馅：
    ① **提交时要回写** `kwInput`（框里带空格的话，得让它显示成真正搜的那个词 —— 所见即所搜）；
    ② **清空要一起清**（只清一级 = 框里还留着字，看着还在搜）；
    ③ **提交后必须收起面板** —— 面板挂在条子下面，不收的话盖住的正好是结果第一屏，她搜完什么都看不见，会以为「没搜着」。
    🔴 **2026-09-30 修正**：这条原先的头一句是「一个输入框同时驱动两件事的时候……」——
    那时这个框除了搜主列表**还负责缩场次清单**。✅ 那个做法已被**方案 B 拆掉**（见第 24 条），
    现在 `kwInput` **不驱动任何东西**，就是个框里存着的字。**两级状态本身留着**，
    但理由只剩后半句那个（打字不搜 / 提交才搜），跟「驱动两件事」无关了。
19. **不是问句的那种弹框，⛔ 不要给它第二个键。**
    「这一场还有 3 张预约单」是个**告知**，不是征求意见 —— 所以 `showCancel:false`，只留一个「知道了」。
    给了「取消」键的话，她会以为那个「取消」＝ 取消档期，点下去什么都没发生，比不弹更糟。
    和第 12 条是一对：**是问句就二次确认 + 把后果写进 `content` + 键文案写动作本身；不是问句就一个键、把「为什么不行 + 怎么办」写清楚**。
20. **页面上根本没有键盘的时候，⛔ 不要调 `wx.hideKeyboard()`。**
    用户报的「**按钮点了没响应**」多半就是它：`hideKeyboard()` 会**打断当前这一次触摸序列**，
    紧跟其后的 `wx.showModal` 在部分基础库上会被整个吃掉 —— 表现正是「点了一下，什么都没有」，**且不报错**。
    档期列表上**一个输入框都没有**，不可能有键盘开着，这个调用在那里等于纯风险。
    ⚠️ 反过来说，**详情页那两个留着是对的**（`cancelSlot` / `cancelLunch`）—— 那一页真有编辑框，键盘可能开着。
    ⚠️ 判断标准不是「习惯性先收一下键盘」，而是「**这一页此刻有没有可能开着键盘**」。
    自测⑧里有一条断言专门钉住这个（`hideKeyboard` 打桩计数必须为 0）—— 它绿着才代表这条路没被「顺手加回去」。
21. **一张卡片整面都能点的时候，卡片里的小按钮要给一段【点得到的】间距，点击区必须【套一层壳】把这段间距圈进去。**
    这就是「**按钮点了没响应**」的第二种长相：妆娘点的是**卡片**，不是按钮。
    病灶通常不在按钮上，在那句 `flex:1` —— 它让名字吃满整行，把按钮推到卡片最右边、紧挨着「›」，
    于是名字和按钮之间留出一大片**看着像按钮、其实是卡片**的空白。手指落在那里 → 进的是详情页，
    妆娘的说法是「我点了取消，怎么没取消」，用户的说法是「**隔这么远容易误触进入此场次**」。
    ✅ 现在的几何（2026-09-30 用户原话：「漫展名称**最多 8 个中文字符**」「在漫展名称 **8 字符占位右边隔一个字符**」）：
    **名字写成【定宽 `width:8em`】**（＝最多 8 个中文字，超了 `text-overflow:ellipsis` 打省略号）→
    **空一个字符** →「取消场次」。
    ⚠️ 定宽比「跟着名字走」好在**按钮横坐标不随名字长短浮动**，靶子位置可预期 —— 这正是被「点不中」坑过之后要的。
    ⛔ 名字里**不许再出现 `flex:1`**（自测 ⑧ 读 wxss 原文钉住这一条）。
    小签外面套一层 `.s-cancel-hit`，**事件挂在壳上**，壳用 **`padding-left:1em`** 把小签【和那一个字符的间距】一起圈进来。
    ⚠️ **⛔ 这里不要用 `margin-left` 做那段间距** —— margin 是**点不到的空白**，正是要消掉的东西。
    ⚠️ 小签本身二十几号字，**总高只有五十几 rpx**（微信的点击区建议是 88rpx），
    所以壳要 `align-self:stretch` + **`min-height:88rpx`** 把命中高度撑够 —— 不然手指偏一点就落到卡片上。
    ⚠️ **⛔ 别给这种小签加 `hover-stop-propagation`。** 试过，撤了：它只在这一个元素上出现过，
    而「点了没动静」正好是加它那一轮变的；它换来的只是「按按钮时别把卡片也点亮」这点观感，
    拿一个说不清的风险换观感不划算。**全项目**只有这里试过这个属性，其余地方的 `hover-class` 一直是好的。
    ⛔ 这一条**自测钉不住排版**（node 里没有排版引擎），只能钉**结构**：自测⑧读 `schedule.wxss` 原文，
    断言 `.s-name` 里不再有 `flex:1`、有 `width:8em` + `white-space:nowrap` + `text-overflow:ellipsis`，
    壳里有 `padding-left` 且 `min-height:88rpx`、小签自己**没有** `margin-left`；
    再读 wxml 断言「接事件的是壳」、用的是 `catchtap`、且**没有** `hover-stop-propagation`。
    ⚠️ 具体的像素值**故意不钉**（88rpx 是微信的建议值，那一条钉住）—— 间距给多少是拿眼睛定的，钉死了每次调都得改断言。
    ⚠️ 断言里查 wxml / wxss 时**要先把注释摘掉**（`<!--…-->` 和 `/*…*/` 两种都要）：
       注释里往往正写着「别再加某某属性」，不摘的话断言查的是自己的说明文字。
22. **每一个分支都必须【出声】，⛔ 尤其是兜底分支。**
    「点了没动静」查了两轮没根治，第三次才发现真正的原因不是按钮坏了 —— 是那个
    `if (!s) { this.onShow(); return }` 的**静默兜底**：卡片过期时它悄悄重画一下，
    于是「**卡片过期**」和「**按钮坏了**」在妆娘眼里长得**一模一样**，都是「点了什么都没发生」。
    查问题的人（我）看到的也是同一个现象，所以两轮都在猜 —— 猜错了两次。
    ✅ 兜底分支必须给一句人话（`wx.showToast` 也行）：她看到「这一场已经不在了，列表刚刷新」
    就知道是列表旧了，而不是「我没点中」，反馈链就闭合了。
    ⚠️ 同理，破坏性动作的入口在**排查期**可以临时加一行 `console.log`，
    让「**这一下到底有没有进到函数里**」变成可分辨的两件事 —— 这是把「猜」换成「测」最便宜的一招。
    定位完就删。自测里把这一行吞掉（`console.log` 打桩），另外留一条断言证明它确实会打。
23. **⛔ 别拿「过滤过的列表」当写回 storage 的底稿。**
    真 bug（2026-09-30 修）：`addSchedule` / `updateSchedule` 原先都从 `getSchedules()` 拿列表 ——
    而 `getSchedules()` 是**滤掉 `cancelled` 的**。于是「新建一场」或「改一场档期」会把过滤后的列表
    整份写回，**已取消的那些记录被顺手真删了**（`cancelSchedule` 的软删除白做了）。
    路径短得离谱：取消 A → 点开 B 的详情页（`onLoad` 里就有一次 `updateSchedule`）→ A 的记录没了。
    而用户被明确告诉过「记录还留着」。
    ✅ 读和写分开：**展示**用过滤后的 `getSchedules()`，**写回**必须用原始列表（`rawList()`）。
    ⚠️ 这种 bug 自测**很容易绿着放过**：断言只查「刚取消完那一瞬间」那一帧。
    要抓它就得**在中间插一次别的写操作**（本轮就是先 `addSchedule` 一个探针场次、再 `updateSchedule` 它，
    然后回头查那条 `cancelled` 记录还在不在）。
24. **一个输入框 ⛔ 不许挂两套搜索范围 —— 范围不一样就拆成两个控件。**
    🔴 真 bug（2026-09-30 用户报的，症状是「**过程有问题**」）：预约单那条条子上，

25. **「下结论」的文案必须和当前筛选范围同口径 —— 范围一变，先回头看有哪些话已经没资格说了。**
    🔴 真 bug（2026-09-30 用户改的，紧接第 24 条）：搜索的**范围掉了个头** ——

    ✅ 结论：**这一句追问省掉了整整一轮瞎猜**（前两轮都是直接去查事件绑定、查 `catchtap`、
    查 `hideKeyboard`，两轮都猜错）。**同一个词在这一个项目里已经有过四种完全不同的病**：
    触摸序列被打断（20）· 按钮被顶到卡片另一头（21）· 兜底静默（22）· **压根就没做（26）**。
    ⚠️ 本轮还有一条印证：**用户在同一条消息里往往已经把答案说出来了** ——
    他这次说的「设置点进去有我的资料，这个删掉，模块重复了」就是**他自己诊断出的重复入口**，
    照做即可，不用验。
    📌 配套：**这一轮的两个落点页一个键都没放** —— 只读页和空态页**整页没有 `bindtap`**，
    于是从结构上就不可能再出「点了没反应」。**拦不住的东西就别画成按钮。**
27. **换数据源之前，先把「同一个来源还喂着谁」整个找一遍 —— 包括那个 import 它的地方是不是绕开了某一层。**
    第十七处把 4 个消费者从 `ARTIST_PUBLIC` 换成 `artistStore.getArtist()`，**找的时候才撞见**

    **⛔ 不要只改你手上那一页**。这次的真实收益是：妆师端「代填」开始**新建**单子之后，
    顾客端和妆师端仍然读的是**同一个数组**，不会演成「她代填了一张、顾客那边看不到」。
28. **你选了「把坏情况藏起来」，就得用更精确的话把那个「空」还回来。**
    用户 2026-09-30 定的：代填的妆位下拉里**只列还空着的**（已订的那几行直接不出现）。

    ⇒ **必须分成三句话**，⛔ 不许并成「没有可选的妆位」（第 22 条：并着报，她就只知道「不行」，
    不知道下一步该干什么 —— 而这三支的下一步是**三个不同的动作**：去建档期 / 去排妆位 / 换一场）。
    📌 判据一句话：**你藏起来的那条信息，用户能不能从别处推出来？** 推不出来，就得用文字补上。
    ⚠️ 这是第 25 条（「下结论的话必须和当前范围同口径」）的**同一件事的另一面**：
    第 25 条管**范围变了**，这条管**你主动少给了一部分信息**。
29. **拆掉一处「拦截」之后，先去找那些「不拦、直接丢」的地方。**
    第十八处（自填风格词）开工时的第一张表就是干这个的：整个链路里 **5 处**会让自填词消失，
    而其中**只有 1 处会报错**（`validateStyleTags` 判它非法、整批拒掉 —— 她自己会发现），
    另外 4 处**全是静默的**（读的时候 `filter(词表内)`、`buildStyleText` 把它排到最后、
    `toStyleOptions()` 的输出根本由 `STYLE_GROUPS` 定死 ⇒ **存得进去、渲染不出来、下次整体丢掉**）。
    📌 判据一句话：**会报错的那处你自己会看见；静默丢掉的那处不会。**
    ⛔ 所以「把拦截改成放行」只是**第一步**，改完必须**顺着数据再走一遍全程**（写 → 存 → 读 → 算 → 画）。
    ⚠️ 同样的道理适用于**写回**：`saveArtist` 的 `next` 是逐字段重建的，
    新字段漏接一次，就是「改一次昵称＝她的自填词全没了」+ 屏幕上弹一句「已保存」（第 23 条的同族）。
30. **用户挑了一个界面形态，就先把这个形态隐含的【数据结构】写下来 —— ⛔ 别为了少写一个字段，偷偷改掉他挑的那个形态。**
    「点自己的词＝勾选、点旁边的 ✕＝删掉」这句话本身就推出：**「在列表里但没选用」是一个必须被保存的状态**
    ⇒ `style_custom` 的每一项**必须带 `on`**。而**扁平的那份并集 ⛔ 不落库**（它是派生值，第 16 条）。
    📌 反过来说：**当你发现要多存一个字段时，先回去看一眼用户挑的是不是别的形态**，
    而不是把两件事压成一个字段（压了就会长出「删不掉、又还在分享页上」的词）。
31. **现成的断言挡住你的时候，先分清它是「过时的期望」还是「在保一个你正要破坏的性质」。**
    第十八处差点栽在这上面：设计初稿让 `style_tags` 存**并集**，于是「校验器拒词表外的词」那条老断言看红了。
    当时的正确动作是**改我的设计**（`style_tags` 保持闭合），⛔ 不是改那条断言 ——
    它保的正是「预设通道只装预设词」这个性质。而同一轮里 `toStyleOptions` → `toStyleView` 那几条，
    挡住的才是**过时的期望**（函数改名了），那几条就该改。
    📌 判据一句话：**这条断言说的那个「不应该发生的事」，是不是我正打算让它发生？** 是 ⇒ 改设计；不是 ⇒ 改断言。
32. **用户能挑的「外观」，一律存【令牌】，⛔ 不存样式值。**
    第十九处的头像颜色：storage 里存的是 `'rose'` / `'blue'`（令牌），⛔ 不是 `'#C0556E'`（色值）。
    令牌 → 色值的映射**只住 `app.wxss` 的 `.c-*` 里**（一处实现，第 11 条）。
    两个理由：① storage 在本机**可以被手改**，M1 还要挪到云端、而云的写入口是客户端 ——
    存样式值等于把一个**任意字符串**接进 `style="…"` 的位置；② 令牌是个**闭集**（6 个），
    配一个**全函数**回落（`avatarColorOf`）之后，「画不出头像」这个状态**从结构上不存在**。
    📌 判据一句话：**这个值将来会出现在 `style=` / `class=` 里吗？** 会 ⇒ 把它变成令牌。
33. **往外发的东西，⛔ 不夹带任何本机已有的隐私，哪怕它「反正她填过」。**
    第十九处的反馈**只写 `{text, created_at}`** —— 妆娘的昵称、城市、微信号**一个都不进那条记录**。
    它们在本机 storage 里放着，顺手 `...artist` 一行就能带上，而那条记录是**发到开发者那儿去的**，
    和「顾客能不能看见」是两回事。`created_at` 走 `db.serverDate()` 也同理：
    设备时间**可以被用户改**，服务端时间不能。
    📌 落点：自测里钉的是**写入对象的键名恰好是 `created_at,text`**（多一个键就红）。
34. **一条没有失败分支的路，要把它「为什么不用出声」写下来 —— 否则下一个人会来补一个 toast。**
    `avatarColorOf` 是全函数（任何输入都回落到 `rose`）⇒ 它**永远不会失败** ⇒ 第 22 条不适用。
    但第 22 条的字面意思是「每个分支都要出声」，一个只读字面的人会认为这里**漏了一个分支**，
    于是加一个 `if (!token) showToast(...)` —— 那是一句**永远弹不出来**的话（死代码），
    而它会让下一个读代码的人以为「这里有失败的可能」。
    📌 判据一句话：**这一段没有出声，是因为「没有失败」，还是因为「失败了没说」？** 前者写进注释，后者是 bug。
35. **配置项（环境 ID / 开关 / 域名）的断言，要么对两种状态都成立，要么明写它按状态分。**
    第十九处的云端投递那一段**故意**写成两支（配好了 → 真的 `.add()` 一次；没配 → 一次都不发 + 出声），
    **两支都必须绿**。⛔ 如果只写「配好了」那一支，那么**配置空着的时候整套自测会红** ——
    而配置空着恰恰是**开工时的常态**（云环境只能由账号持有人开）。那一天多半会有人
    把这条断言改松（「反正环境还没配」），于是**「配没配都不能静默」这条性质就永久丢了**。
    📌 代价要认：**「全绿」的条数会跟着配置变**（**1291** 是已填时的数）—— 所以在 §3.6 里写明这件事。
36. **一份列表的"长度"从哪来，决定了它合不合规 —— ⛔ 不是"它长什么样"。**
    第二十处的「我约过的妆娘」看着就是一份妆娘列表，但它的长度来自
    **「我自己提交过的那张预约单」**（`created_by === 'user'`），所以它是一份**私人记录**；
    同样一屏，只要长度改成来自「目录里有几个人」，它当场变成一份**能被一页页翻完的公开目录**（红线 1）。
    ⇒ 在个人主体下这不是取舍，是**唯一合规的形态**（详见 §3.7）。
    📌 落点：**演示数据也必须自洽** —— 列表里有她，就必须有一条"我约过她"的单撑着她。
    自测里正向反各钉一条。**改了判据不会报错、页面还更好看**，所以必须钉死。
    📌 判据一句话：**这一页上出现的东西，是"我自己的记录"，还是"所有人的名单"？**
37. **用户说「照 A 那样做」的时候，先确认是【搬】还是【抄】——默认是搬。**
    第二十处顾客端要一个"妆娘主页"，现成的是 C1 落地页（`pages/landing/`）。

38. **一个值有【两个数据源】的时候，"谁提供"和"谁消费"必须经过同一个模块 —— 数据源清单只许一处知道。**

    📌 判据一句话：**"这个东西还在吗"这句话，两侧问的是不是同一个来源？**

39. **做测试数据的时候：入口只要带了「是哪一位」，就必须至少喂两位进去。**

    而代码要保的性质是「**任意一位**妆娘的妆位都通」。

       （写死的话，改示例数据时它会红，而红的原因跟它要保的性质无关 —— 那是假红，久了没人信）。

40. **测试自己先站稳：用例里那条数据，必须满足被测路径的前提。**

    📌 判据：**这个用例要证明「A 能成」，那它喂进去的数据就必须真的满足 A 的前提。**
       ⛔ 别用「反正跑得通」的旧数据凑合；⚠️ 也别写死序号 —— 当场算一个空位，

41. **「能不能分享」不是一个开关，是【每个页面各自的一件事】—— 所以判据必须能扫，而且要先摘注释。**
    微信的官方规矩是「**只有定义了 `onShareAppMessage`，右上角菜单才显示「转发」**」。
    于是「这个小程序能不能分享出去」实际上是 **18 个页面各自的一件事**：
    漏一页，那一页点「···」里就没有「转发」—— **不报错、不白屏、没有任何别的信号**。
    📌 2026-10-02 之前的真实状态：18 页里只有 `pages/schedule-edit/` 一页有。
       ⚠️ 见规矩 42：`app.wxss` 里那组 `.btn-share` 曾**早就写好、却一次没用过**
       —— 「样式备好了」和「按钮造出来了」中间隔着这一步，光有前者什么也证明不了。
       （那组样式已在第二十六处删掉，因为用户不要页面内的分享按钮。）
    ⇒ 三条一起做：
      ① 卡片内容收拢到 **`utils/share.js` 一处**，每页只留一行
         `onShareAppMessage() { return shareCard(this.artistId) }`；
      ② 自测**扫 `app.json` 里的每一页**，断言它接上了那一个函数；
      ③ 扫之前**先摘注释**，并给扫描器喂一段「这一行被注释掉」的合成源码 ——
         否则「谁哪天顺手把它注释掉」这种最隐蔽的回归会被放过（规矩 35）。
    🔴 同一个坑的另一面：`shareCard` 的形参**只能叫 `artistId`，⛔ 不能是 `options`**。
       微信调它时第一个参数是 `{from, target}`；写成 `shareCard(options)` 会拼出
       `…?artist_id=[object Object]` —— **不报错、卡片照发**，只是点开落到兜底那位。
       自测里专门有一条喂对象进去。⚠️ 同理，页面跳转用的 `url:` 和分享用的 `path:`
       **差一个词**：拿「落点 URL 的字面量」当违规判据会误伤 C1 的正常跳转（假阳性）。

42. **一段代码「读起来像在做 A」，不等于它真的在做 A —— 汇报「已接入」之前，先问它到底改变了什么。**
    📌 2026-10-02 第二十六处。用户第一句贴过来的是微信文档里
    `showShareMenu` + `withShareTicket` + `getShareInfo` 那一段，说「**接入转发代码**」。
    那一段**跟「小程序能不能转发」毫无关系** —— 转发按钮出不出现只看页面有没有
    `onShareAppMessage`（规矩 41）。它真正做的事只有两件：把 `shareTicket` 写进
    本地 storage、调一次 `wx.getShareInfo` —— **而后者自基础库 2.17.3 起已停止维护**，
    拿到手也只有一句 `console.log`。
    ⇒ 教训不是「别照文档写」，是：
      ① **一个 API 被调用了，不等于它产生的结果被用上了** —— 汇报之前先追一遍
         「这个返回值往下走到哪」，走不到任何地方的就是**没有功能**；
      ② 比「没有功能」更麻烦的是**它顺手造出了一条对外声明**：那块死代码让
         《隐私保护指引》必须申报「缓存群标识」，而缓存下来没有任何用途 ——
         这是一条**实际不成立的收集声明**，正撞「声明与功能不符」。
         ⛔ 死代码不只占地方，它**会连带别人的文档一起说谎**。
    ✅ 已整块删除：`app.js` 的 `SHARE_KEY` + `onShow`、`schedule-edit.js` 的
       `wx.showShareMenu`、`app.wxss` 的整组 `.btn-share`（同一个来路：为了那个
       从没造出来的 `<button open-type="share">` 先写好的样式），以及
       《隐私保护指引》里全部 shareTicket 字样。自测加了反向断言钉死它们不许回来。

43. **卡片落点控不了，就别在「控不了落点」的地方开分享。**
    📌 2026-10-02 第二十七处（朋友圈）。**转发**和**朋友圈**在这一点上完全不同：
    · 转发（`onShareAppMessage`）**能**自定义 `path` ⇒ 所以 18 页统一落到 C1；
    · 朋友圈（`onShareTimeline`）**不能**自定义页面路径（官方原话：「自定义分享内容时

### 3.7 「我约过的妆娘」为什么不是公域发现（第二十处 · 对外解释的唯一口径）

> 这一节是**给提审写的**。审核员问「这个列表是什么」的时候，答案只有下面这一段；
> ⛔ 不要临场组织语言，⛔ 也不要说成「平台上入驻的妆娘」。

**这一屏是一份私人记录，不是一份目录。** 它的长度 = **你自己约过几个人**，
判据 = **你自己提交过的那张预约单**（`created_by === 'user'`，唯一实现在 `utils/myArtists.js`）。
一次都没约过的人**永远不出现在这一页上**；反过来说，你约过谁，这一页就只有谁。

**为什么必须这样**（三条，从硬到软）：

1. **个人主体没有「社交 / 社区」类目。** 一个能被一页页翻完的**公开妆娘列表**，就是一份
   人肉目录 —— 这正是红线 1。这不是"能不能做出来"的问题，我们已经被驳回过一次，
   而个人主体的封禁**不可解封**。
2. **同一件事我们已经在 §4 第十五处砍过一次。** 妆娘上传作品给顾客看，被驳的原话是
   「涉及用户自行生成内容（图片）的记录、分享，属**社交-笔记**范畴，为**个人主体小程序未开放类目**」。
   一份公开的人肉目录，性质上比那更靠里。
3. **公域发现那条路第十九处就整块砍掉了**（「砍公域发现、不办证」是那一轮定的方向）。
   现在把列表做成目录，等于把砍掉的东西从后门放回来 —— 而且是**最容易被审核抓住的那扇门**。

**演示数据也必须自洽**（这条是硬要求，不是建议）：列表里有她，就**一定**有一条「我约过她」的单。
